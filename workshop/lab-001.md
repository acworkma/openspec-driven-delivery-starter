# Participant lab: 001 dependent-claim privacy

## Learning objective

Deliver one agreed behavior through OpenSpec, business examples, JavaScript,
automated evidence and independent PR review. You are building a **privacy
policy function**, not a production claims portal.

## Timeboxes

| Agenda segment | Minutes | Work |
| --- | ---: | --- |
| 5: Part 1, intent to OpenSpec change | 55 | Steps 1-2; prepare before the day where possible |
| 7: Part 2, design, Given/When/Then and tasks | 45 | Step 3; review readiness and the plan |
| 8: Part 3, implement with Copilot | 60 | Step 4, including checks and catch-up |
| 10: CI, PR review and archive combined | 35 | Steps 5-6; 10 minutes CI, 15 review, 10 archive |

Keep the final [first-spec exercise](first-spec.md) and readout time protected.
Only this lab requires participant coding.

## 1. Prepare an isolated learner repository

From the completed reference checkout:

```powershell
npm run lab:prepare
```

In a new terminal, move into `context\lab-001` on Windows
(`context/lab-001` on macOS/Linux), then:

```powershell
npm ci
git init -b main
git add .
git commit -m "Initialize workshop learner checkpoint"
git switch -c workshop-001-privacy
```

The generator refuses to overwrite an existing directory. To restart, create
a new destination such as `npm run lab:prepare -- context/lab-001-retry`.
Do not delete or reset another participant's working copy.

Use your platform's instructions to connect this **learner repository** to an
empty sandbox remote. Do not push the facilitator's `.git` or nested `context`
directory. Publish the initial checkpoint to the remote default branch before
opening the feature PR; the feature branch must have a real diff.

## 2. Frame and clarify

Read [the intent brief](cases/001-member-claim-status/intent-brief.md) and the
broader `openspec/changes/add-member-claim-status/` proposal for context.
Your actual delivery change is `openspec/changes/implement-dependent-privacy/`:
read its scoped proposal, delta, design and tasks. Use [the worksheet](pair-worksheet.md).
Complete its [Assumptions, dependencies and test data](pair-worksheet.md#assumptions-dependencies-and-test-data)
section: name who confirms privacy fields and lookups, identify upstream and
downstream dependencies, list at least three edge cases and map synthetic
data to each acceptance scenario. Distinguish supplied test flags from verified
production capabilities.

Product owner: confirm that under-13 claims are visible unless confidentiality
blocks them, ages 13-17 exclude sensitive claims, adults are private, and
unknown privacy facts fail closed. These rules are fictional training policy.

Architect: distinguish caller-supplied age/privacy facts and simulated
authentication flags from production identity/authorization. No real records.

Record the actual decisions and the slice's non-goals in the proposal.
Do not mark all broader 001 requirements implemented.

## 3. Agree on examples and plan

Review `features/claim-status.feature` and the design together. Use the
[prompt cards](prompts.md) to ask Copilot for a plan, without editing first.

The learner copy intentionally replaces only
`src/claim-visibility.js` with an explicit missing-implementation error.
Keep the supplied projection, lookup, unit tests and Gherkin unchanged.
Add a new scenario only when the team explicitly agrees on a behavior change.

Confirm [Ready to build and Plan accepted](../docs/operating-model.md#four-human-gates)
with the responsible humans before implementation. Missing material facts
remain blockers. Run:

```powershell
npm run lab:test
npm run lab:bdd
```

Both should fail with the missing-policy error. A failing command is expected
**only in this learner checkpoint**, not in the reference checkout.

## 4. Implement the approved slice

Use 10 minutes to restate the approved plan, 30 to implement and inspect, and
20 for evidence or catch-up. Ask Copilot to implement `canViewDependentClaim`
in the one policy file.
Inspect the diff. Do not weaken tests or reveal hidden claims through totals.
Unknown/non-integer ages and missing privacy flags must deny visibility.

Run the targeted checks again, then:

```powershell
npm run check
npm audit --audit-level=high
```

Explain why the code now passes. Automated output is evidence, not approval.
If you change an actual requirement or source scenario, update the reviewed
inventory and contract deliberately; the traceability check will report drift.

### Catch up and move on

If implementation is unfinished after 40 minutes, preserve the current policy
as `context\claim-visibility-attempt.js` in your learner copy. With the
facilitator, copy only the completed reference `src\claim-visibility.js` from
the workshop's main reference tree into the learner's `src\claim-visibility.js`
(for the default layout, run `Copy-Item ..\..\src\claim-visibility.js .\src\claim-visibility.js`
from `context\lab-001`). Do not use `git restore --source=main`: the learner's
initial `main` checkpoint deliberately contains the missing-policy stub.
For another learner location, use the facilitator's verified reference path.

Inspect the restored rule together, rerun targeted checks and `npm run check`,
and move to review. Record **reference-assisted catch-up**, not independent
implementation, in the readout. Do not overwrite another pair's work, change
tests, or bypass missing human decisions to catch up.

## 5. Open a PR and get independent review

Follow the [GitHub path](../docs/path-github.md) or
[Azure DevOps path](../docs/path-azure-devops.md). Link the issue/Boards item,
OpenSpec change, scenario IDs, code and check results. Review the small policy
diff and require another person to inspect it.

Only mark the human review tasks complete after the corresponding actions
actually happen. Keep deferred production requirements visible.

## 6. Maintain the living spec

Follow [the archive exercise](archive-exercise.md), inspect the updated
current contract and history, rerun checks and obtain any renewed review.
Record the lab evidence for [the readout](readout-template.md). The combined
35-minute block ends here; [your first spec](first-spec.md) gets its own
70 minutes before the closing readouts.

If platform or approval access is unavailable, state that explicitly. Local
tests alone do not satisfy the hosted PR/CI outcome.
